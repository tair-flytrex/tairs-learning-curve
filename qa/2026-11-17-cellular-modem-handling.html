What do the cellular messages contain, and in general how is the cellular periph handled?

HardwareMessagingServices

Two separate paths read the modem. drone_periph polls the radio measurements every 500 ms and publishes them over RabbitMQ. emc uses them only for the C2 log. emc also has an older, optional poller of its own that reads general modem info with mmcli.

The message: CellularMeasurementMessage

Defined in services/drone_periph/internal_sdk/protos/drone_periph_messages.proto. Each message is one poll, and covers the serving cell only. A field the modem didn't report is left unset.

  • access_technology: NONE (no service), GSM, UMTS or LTE.
  • band: the LTE band number, e.g. 66.
  • earfcn: the downlink channel number. It can go above 65535.
  • pci: the physical cell ID, 0-503.
  • bandwidth_mhz: the cell's bandwidth.
  • Signal:
    • rsrp_dbm: received signal power.
    • rsrq_db: received signal quality.
    • rssi_dbm: total received power.
    • sinr_db: signal-to-noise ratio.
  • mcc, mnc: the network's country and operator codes. They are strings so that leading zeros are kept ("01" and "001" are different networks).
  • sim_slot: always 1, because there is a single SIM.

When the modem isn't on LTE, the message has only the access technology, the RSSI and the MCC/MNC. The LTE cell values could be left over from earlier, so they aren't sent.

drone_periph: reading the modem

  • How it reads the modem: QmiModemClient (qmi_modem_client.py) talks QMI to /dev/cdc-wdm0 through qmi-proxy, using libqmi's Python bindings.
    • It needs root, because qmi-proxy only accepts root.
    • If the bindings are missing, it logs a warning and skips modem polling. The altimeter keeps working.
  • Each poll (every 500 ms): it sends six QMI requests in parallel, each with a 1 s timeout:
    • signal info
    • RF band
    • cell location
    • carrier aggregation (CA) info
    • serving system
    • Sierra Wireless's own status report
  • Parsing: QmiResponseParser copies the plain values out of each reply.
  • Choosing a source for each value (_build_measurement). Each value comes from the source that is most reliable for it, with a fallback:
    • RSRP, RSRQ and RSSI: from cell location, which is measured every poll. The fallback is signal info, which the modem refreshes only about every 3 s.
    • SINR: from signal info only.
    • PCI: from cell location, falling back to CA info.
    • Band and EARFCN: from the RF band report. The other reports carry a 16-bit channel number, which is wrong for bands like 66 and 71.
    • Bandwidth: from CA info, falling back to the Sierra status. CA info has nothing until the first carrier aggregation event after boot. When both sources have a bandwidth and they disagree, it logs a warning.
  • Robustness:
    • If the modem stops answering several polls in a row, it reconnects. A failed connection is retried every 5 s.
    • An enum value libqmi has no name for, such as a band newer than libqmi, is treated as missing, because reading its name would crash Python. It is logged and counted.
  • Flight summary: FlightEndListener subscribes to fcm's AerialStateChanged. On landing, drone_periph logs one summary line covering:
    • how often each fallback was used
    • how often the two bandwidth sources disagreed
    • which unknown values were seen
  • Publishing: CellularPublisher publishes on the cellular fanout exchange with a 1 s TTL.
    • It has its own pika connection, separate from the altimeter's, because pika isn't thread-safe.
    • Measurements sent while RabbitMQ is down are dropped.

emc: using the measurements

  • Receiving: CellularCommunicator (accessories/cellular/) subscribes to the cellular exchange and keeps only the latest measurement. Devices creates it with the other devices.
  • Logging: C2Logger runs from the moment a mission is accepted until it ends. Every 500 ms it writes a c2 sample into the mission's SLog, containing:
    • position and attitude from fcm
    • the latest cellular measurement: rat, cell_type, band, EARFCN, PCI, bandwidth, signal values, MCC/MNC and SIM slot
    • when each part was received
    Once per mission it also writes a header with the modem model and firmware.
  • Who sees it: the measurements aren't sent to the GCS live. They only reach the C2 log, which is uploaded with the mission logs.

emc's own modem poller (optional)

CellularInfoPoller (logic/) is used only when the use_cellular_info_poller setting is on. That setting is off by default. Every cellular_polling_period_ms (1000 ms by default), it runs mmcli -m <modem> --output-json through ModemManager. It also follows the active modem, which changes when the eSIM profile changes. It reads:

  • the access technologies
  • IMEI
  • operator code and name
  • registration and packet-service state
  • whether a SIM is present
  • the modem model and firmware revision

It is used in three places:

  • On mission accept: emc sends CellularModemInfo to the server (report_cellular_modem_info, ReportCellularModemInfoRequest in mc_gcs_sdk).
  • In the C2 log header: the modem model and firmware come from this poller. They were removed from CellularMeasurementMessage (fields 13 and 14 are reserved).
  • The status LED: when the server connection fails, ConnectionStateIndicator turns it blue. It blinks if a SIM is present and stays solid if there is none.

Elsewhere

system_config uses mmcli once at startup to allow every modem band.
