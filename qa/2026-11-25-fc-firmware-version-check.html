In the code, is there something that checks the firmware version struct from the FC?

OTA & firmwareMessaging

Yes. The struct is the MAVLink AUTOPILOT_VERSION message. The FC's copy is read in two places, but only one of them compares the version against anything.

1. firmware_updater: the only real check

  • get_current_version() in services/firmware_updater/firmware_updater/updater/mavlink_updater.py (line 116) waits for a heartbeat with system_status of standby or above, sends MAV_CMD_REQUEST_AUTOPILOT_CAPABILITIES up to 3 times, and waits for AUTOPILOT_VERSION.
  • It returns the formatted middleware_sw_version. That is the Flyhawk version. flight_sw_version is the ArduCopter base and is not compared.
  • update_if_needed() in updater/base.py (line 64) compares it to the profile's target_version. Equal: nothing to do. Different: flash. Unreadable after the retries: flash anyway, because can_flash_without_version() is true for MAVLink devices. A board sitting in its bootloader counts as 0.0.0.
  • verify_update() reads the version again after the flash and fails the update if it is not the target.

2. fcm: decodes and publishes, no validation

  • fcm requests AUTOPILOT_VERSION once at initialization (ardupilot_fc_commander.py, _request_mavlink_messages_on_initialization).
  • main.py routes the reply to AutopilotVersionToFcVersion (fc_state/mavlink_to_proto_converters/autopilot_version_to_fc_version.py). It logs every field of the struct and publishes a UavcanComponentVersion on the UavcanComponentVersion_fc topic.
  • The published string looks like Flyhawk <middleware> <flight_custom> (ArduCopter <flight_sw>) (HW id: <uid2>).
  • Each 32-bit version is unpacked as four bytes: major, minor, patch, type. The type byte becomes a -dev, -alpha, -beta or -rc suffix, or nothing for an official build.

Who reads that string

  • software_updater: FirmwareVersionParser in firmware_versions.py takes the first dotted triple (for example 5.4.6), and ModuleVersions rolls it up per device for the report to Oversight.
  • emc subscribes to the same topic in FcmCommunicator.java (latestUavcanComponentVersionFc).

The FTS has the same thing in emc

  • FlytrexFts.processAutopilotVersion() handles the FTS's own AUTOPILOT_VERSION. It logs it with MavlinkConnectionWrapper.logAutopilotVersion(), builds the string with getFcVersion(), and emc publishes it as FtsVersion. Despite the name, getFcVersion() is only called for the FTS.

What does not exist

  • There is no minimum-version or compatibility gate. Nothing refuses to arm or fly because of the FC version.
  • MavlinkConnectionWrapper.hasCapability() can test the capabilities bitmask, but nothing calls it.
  • Side note: autopilot_version_to_fc_version.py line 20 has a leftover debug print("RAZFCM: ...").
